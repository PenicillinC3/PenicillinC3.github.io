🎉 欢迎参与项目开发与维护！为保证项目代码整洁、版本迭代规范、提交记录清晰，本文档统一规定了 **代码提交规范**、**版本发布规范** 与基础开发流程，所有代码提交、版本发布均需遵守本规则。

---

## 一、前置说明

1\. 项目默认主分支：`main`（稳定发布分支，禁止直接推送临时代码）

2\. 版本规则：严格遵循 **语义化版本 SemVer**，格式：`v主.次.补丁`

3\. 所有提交记录、版本 Release 日志统一规范化，拒绝模糊提交（update、modify、fix bug 等无效描述）

---

## 二、Git 提交规范（核心）

### 2\.1 提交格式

固定格式：`<type>(<scope>): <description>`

- **type（必填）**：提交类型

- **scope（可选）**：模块/功能范围，如 login、home、api

- **description（必填）**：简短清晰的中文改动描述，冒号后必须加空格

### 2\.2 全部提交类型对照表

| 类型       | 使用场景说明                                                   |
| ---------- | -------------------------------------------------------------- |
| `feat`     | 新增业务功能、新增页面、新增接口                               |
| `fix`      | 修复线上/测试 Bug、逻辑异常、报错问题                          |
| `docs`     | 仅修改文档：README、注释、使用说明，无代码逻辑改动             |
| `style`    | 代码格式优化：缩进、空格、分号、换行，**不改变代码逻辑与功能** |
| `refactor` | 代码重构、结构优化、抽离公共方法，无新功能、无 Bug 修复        |
| `test`     | 新增单元测试、修改测试用例、调整测试代码                       |
| `chore`    | 杂项维护：更新依赖、修改配置文件、调整 gitignore、打包配置     |
| `perf`     | 性能优化：加载速度、渲染优化、接口请求优化、代码瘦身           |
| `ci`       | CI/CD 流水线配置、GitHub Actions、自动部署脚本修改             |
| `build`    | 项目构建、打包编译、构建依赖、编译规则调整                     |
| `revert`   | 回滚历史某次提交、撤销错误代码改动                             |

### 2\.3 标准提交示例（可直接复用）

```bash
git commit -m "feat: 新增用户登录功能"
git commit -m "feat(home): 新增首页轮播模块"
git commit -m "fix: 修复按钮点击无响应问题"
git commit -m "docs: 更新项目部署与启动文档"
git commit -m "refactor: 抽离公共请求工具函数"
git commit -m "chore: 更新项目依赖版本"
git commit -m "perf: 优化静态资源加载速度"
git commit -m "revert: 回退上一版接口改动"
```

### 2\.4 禁止行为

- 禁止使用模糊备注：`update`、`modify`、`更新代码`、`修复bug`

- 禁止一次性提交大量无关改动，建议功能拆分、分批提交

## 三、日常代码更新推送流程

适用于本地修改代码后，更新到 GitHub 仓库的标准流程

```bash
# 1. 查看文件改动（可选）
git status

# 2. 暂存所有改动
git add .

# 3. 规范提交代码
git commit -m "type: 改动说明"

# 4. 拉取远程最新代码（避免冲突）
git pull origin main

# 5. 推送到远程仓库
git push origin main
```

## 四、版本 Release 发布规范

### 4\.1 版本号规则（SemVer 语义化版本）

格式：`v主版本.次版本.补丁版本`

- **主版本\(X\)**：不兼容破坏性改动、项目大重构、架构升级

- **次版本\(Y\)**：新增功能、新增模块，兼容旧版本

- **补丁版本\(Z\)**：Bug 修复、细节优化、小调整，无功能新增

示例：`v1.0.0`（首个正式版）、`v1.1.0`（新增功能）、`v1.1.1`（修复bug）

### 4\.2 本地创建 Tag（版本标签）

Release 必须依赖 Git Tag，先打标签再发布版本

```bash
# 创建带备注的版本 Tag
git tag -a v1.0.0 -m "Release v1.0.0 正式版本发布"

# 推送 Tag 到远程仓库（普通 push 不会推送 tag）
git push origin v1.0.0

# 查看所有本地版本标签
git tag
```

### 4\.3 GitHub 网页创建 Release 步骤

1. 进入仓库主页，点击右侧 **Releases**

2. 点击 **Draft a new release** 新建发布版本

3. **Choose a tag**：选择/创建对应版本 Tag（如 v1\.0\.0）

4. **Target**：选择稳定分支 `main`

5. **Release title**：填写版本号（如 v1\.0\.0）

6. **Describe this release**：填写标准化更新日志（可使用下方模板）

7. 可选：上传打包文件、exe、zip 等资源到 Assets

8. 预发布版本勾选：**This is a pre\-release**

9. 点击**Publish release** 正式发布

### 4\.4 Release 日志统一模板

发布版本时直接复制使用，分类清晰、适配所有迭代

```markdown
## v1.0.0
### ✨ 新增功能（Features）
- feat: 项目基础核心功能开发完成

### 🐛 问题修复（Bug Fixes）
- fix: 修复已知功能性问题

### 📚 文档更新（Docs）
- docs: 完善项目使用与部署文档

### ⚡ 性能优化（Performance）
- perf: 优化项目加载与运行性能

### 🛠 项目维护（Chore）
- chore: 优化项目配置与依赖版本
```

## 五、常用注意事项

- 禁止随意删除远程 Tag 和 Release，会导致版本记录丢失

- 重大版本迭代、功能新增、Bug 修复必须单独打版本发布 Release

- 每次发布前保证 `main` 分支代码可正常运行、无严重 Bug

- 单人项目可轻度简化，但提交类型、版本号规则必须遵守
